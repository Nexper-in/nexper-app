# Nexper: project record

A running record of what has been decided and built, so a new session (or a
person) can pick up without the chat history. Last updated 2026-10-01.
Nothing here is a secret. Keep it that way. Rules for changing the code are in
`CLAUDE.md`; this file is the history and the open list.

## 1. What Nexper is

A billing, stock and udhaar (credit) app for small Indian shops (kirana,
supermarket, auto parts, clothing). Web plus installable phone app (PWA).
Brand **Nexper**, domain **nexper.in** (it was SabStore, briefly "Nammalekka").
Main user: one person who is owner and helper at the counter. Goal: a new owner
makes the first bill in under 3 minutes. Simple beats everything else.

## 4. Phone and laptop are separate screens (decision, 2026-10-01)

Abdul: "We can keep web and mobile separate." Chosen option: **separate
screens, same app and same login.** Do not go back to one stretched layout.

- Phone is below 1024px, laptop from 1024px (`lib/useIsMobile.js`).
- Each of Home (`app/(app)/dashboard`), New bill (`billing`), Stock
  (`inventory`) and Udhaar (`credit`) has `use<Screen>.js` (all data, state and
  actions), `<Screen>Mobile.js`, `<Screen>Desktop.js`, shared
  `<Screen>Parts.js` where needed, and `page.js` choosing between them.
  Change behaviour once in the hook; change layout in the screen that needs it.
- **Phone stays lean.** **Laptop uses the room:** Home shows the whole dashboard
  (numbers, week chart, categories, customers, stock movement); New bill puts
  items and the bill side by side; Stock shows totals and every tool as a
  button; Udhaar adds a "Customers who owe" count.
- Other pages (Bills, Reports, Expenses, Cashbook, Suppliers, Staff, Day close)
  are still one responsive layout (stacked cards on phones). Split one only
  when it needs a different laptop design.

## 5. App stack

- Next.js 15 App Router (JavaScript), Tailwind plus `ks-*` classes and theme
  tokens in `app/globals.css`. Never hard-code colours.
- Supabase: Postgres with row-level security, Auth (email + password for
  owners; staff code + PIN), `supabase/schema.sql` plus migrations `001`-`030`.
- Server routes under `app/api/` use the service-role key and an Anthropic call
  (`/api/scan-supplier-bill`).
- Env vars: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`,
  `SUPABASE_SERVICE_ROLE_KEY`, `ANTHROPIC_API_KEY`; optional
  `NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_SUPPORT_EMAIL`,
  `NEXT_PUBLIC_SUPPORT_WHATSAPP`, `NEXT_PUBLIC_GOOGLE_SIGNIN` (see below).
- Languages: English text is the key, `t()` from `useT()`, translations in
  `i18n/*.json`, `npm run check:i18n` fails on gaps (also run by GitHub).
- Pro plan gating is paused: switch it on from the platform console (Pricing & tax, "Enforce plans").

### Supplies for tea shops, canteens, hotels (branch work, 2026-10-02)

Asked for by a tea-shop owner who supplies tea and biscuits to the departments of a
hospital. A new shop type "Tea shop / Canteen / Hotel" starts with the **Supplies**
screen (`/supplies`) on and credit/supplier screens off. **Daily round:** the helper
comes back, then someone enters how many of each item went to each department for the
day (any date, "copy the day before"); saving again corrects instead of doubling.
**Accounts:** what each department owes; departments pay daily or monthly, so a
statement can be made for today, this week, this month, last month or any dates, sent
on WhatsApp, and payments are recorded against it. Price is the item's price (same for
every department so far); the price on the day is kept. A helper login can be given only
the Supplies permission and then lands straight on it. Not built yet: departments or
customers placing orders themselves, signed slips, per-department rates, stock
deduction, working offline. Tables `supply_points`, `supply_entries`, `supply_payments`
(shared by all shops, `shop_id` + row-level security); entries are written only by
`save_supply_round()`. `npm run test:db` runs the access rules against a real Postgres.

### Platform console (branch work, 2026-10-01)

`/admin` now has Tenants (plan, expiry, limits, feature overrides, API/MCP per
shop), Onboarding (open a shop for someone or send an invite; sign-up mode open /
invite-only / closed), Pricing & tax (Pro price, GST, enforce plans), Features
(global switches and what Free includes), API & MCP (switches, keys, how to use)
and Platform (banner, maintenance mode). Also a read-only REST API (`/api/v1`)
and an MCP endpoint (`/api/mcp`) for Claude and other assistants. Everything is
off or unchanged until switched on. Security notes in `SECURITY.md`.

## 7. Google sign-in (built, switched off)

The button shows with a "Soon" label and does nothing. To turn on:

1. Supabase: Authentication, Providers, Google, enter the Google Cloud OAuth
   client ID and secret.
2. Google Cloud: add `https://<project>.supabase.co/auth/v1/callback` as an
   authorised redirect URI. The old prototype already has a Google client
   (Firebase project `nexper-fd4f1`); reuse or create a new one.
3. Vercel: set `NEXT_PUBLIC_GOOGLE_SIGNIN=true` and redeploy.

Then "Continue with Google" shows first and email becomes a fallback link.

## 9. Practical notes

- Run the app: `npm install`, `.env.local` with the two public Supabase vars,
  `npm run dev`. Signed-in screens need a real Supabase project, or a browser
  test that sets a fake `sb-<ref>-auth-token` cookie and intercepts Supabase
  requests (mocked shops need a populated `enabled_modules`).
- Before pushing: `npx next build` and `npm run check:i18n`; look at changed
  screens in Night and Light, on phone and laptop width.
- Production builds create `public/sw.js` and workbox files; they are ignored,
  don't commit them.
- `pkill -f "next dev"` can kill its own shell; use `[n]ext dev`.
- Commits end with a `Co-Authored-By` and a `Claude-Session` line. Work goes to
  the working branch; `main` only when the owner says so.
